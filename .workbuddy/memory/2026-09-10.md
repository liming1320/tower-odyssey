## ⭐ 云端 ROM 丢失事故根因（当天最重要的发现）
**「只要上传代码，云端 rom 列表就清空」= roms 不在 MySQL META_KEYS，元数据从未持久化**
- `server/store.js` 的 `META_KEYS` 定义哪些全局数据进 game_meta 表，`'roms'` 不在其中

## 17. 模拟器 iframe 高度 CSS bug → 找不到键位设置的根因

**用户反馈**：「控制设置只有重置，清除，关闭，没有设置键位的地方啊」（带截图）

## 18. 模拟器 401 未登录误提示"管理员没上传"（手机看不到游戏）

### 症状
玩家用手机外网 IP 访问 152.136.167.250:5180 看到"管理员还没有上传游戏，敬请期待"，电脑访问 localhost:5180 正常看到 60 个 ROM。

### 根因
不是云端 ROM 库为空，也不是云端代码旧版。
- emulator.js `romList()` 把 `/api/roms` 401（未登录）返回的 `{error:"未登录"}` 用 `(d && d.roms) || []` 吞掉 → 当空数组 → 渲染"管理员还没有上传游戏"
- 手机 localStorage 里 game-token 失效（清理缓存/换浏览器/管家软件清 cookie）
- 但 token 失效前端是 silent 吞掉，玩家完全不知道要重新登录

### 修复
- emulator.js `romList()` 检测 `r.status === 401` → 返回 `{_authError: true}` 标记
- `renderList(roms, authError)` 在 authError 分支显示：
  - 醒目提示："⚠ 登录状态已失效（浏览器缓存被清理 / token 过期）"
  - 说明："电脑正常而手机看不到游戏，多半就是这个原因"
  - 一键【⏏ 退出账号 · 重新登录】按钮（清 token + 刷新跳登录页）
- emulator.js 版本 20260910e → 20260910f
- smoke-emulator.js 加 ⑤.c 测试段：清 token 触发 401 → 验证新提示和按钮

### 验证

### 教训
**API 鉴权失败必须明确区分"没数据" vs "没登录"**。
前端 catch 或 fallback 到空数组会把鉴权失败吞掉，让玩家以为是数据问题，定位极其困难。建议：
- 所有鉴权 API 在 fetch 失败/4xx 时记录明确错误码
- 401/未鉴权走专门的 UI 分支（重新登录/提示），不能走"暂无数据"分支
- 顶层 fetch 封装或拦截器统一处理 401，避免每个调用点都要写

## 2026-09-10 续2 · WebHook 为什么不生效（用户质疑「不是有 webHook 吗」）

### 排查过程（结论：脚本写了但云端从没装过，且脚本本身有个致命 bug）
1. 实测云端 `152.136.167.250`：

   - 8888 → 404（**宝塔面板在跑**）
   - 80 → 200（Nginx 在跑）
   注意：本机 curl 走的是代理 `http://127.0.0.1:56724`，判断端口通不通要区分
   timeout（DROP/防火墙）与 connection refused（进程没监听）。
2. 定位到两个真问题：

**① 致命：`tools/webhook-deploy.js` 的 `runDeploy` 只监听子进程 `exit`，没监听 `error`**
- `spawn('bash', [deploy.sh])` 在 bash 不在 PATH / 脚本路径不对时抛 ENOENT，
  这是 **error 事件而非 exit**，未捕获异常 → **整个 webhook 进程被带崩**。
- systemd `Restart=always` 会不停拉起 → 崩溃循环。
- 外部表现：完全没反应，日志里只有一行 `Unhandled 'error' event`。
- 这正是「配好了但完全不生效」的典型症状，也是我之前误判成「需要手动 restart」的原因。
- **修复**：spawn 前 `fs.existsSync` 检查脚本；加 `child.on('error')` 把原因写进
  `state.last.error`（状态页可读）；`exit` 里加 `if (item.status==='failed' && item.error) return`
  防止覆盖。实测：脚本缺失时返回 `{"error":"deploy.sh 不存在: ..."}` 且进程存活（HTTP 200）。

**② 体验：手改 service 文件太容易出错**
- `deploy/webhook-deploy.service` 里 `ExecStart=/usr/bin/node` 是硬编码，
  宝塔装的 node 在 `/www/server/nodejs/<版本>/bin/node`，照抄必然起不来。
- 新增 `deploy/linux/install-webhook.sh` 一键安装：探测 node（复用 detect-node.sh）、
  openssl 生成密钥、写 systemd（带探测到的 node 绝对路径 + PATH）、
  daemon-reload + enable + restart、本机自检 curl、按监听地址分别打印 Gitee 配置指引。

**③ 免开端口方案（推荐）**
- 新增 `WEBHOOK_HOST`（脚本默认 127.0.0.1）。
- `deploy/nginx/tower-odyssey.conf` 新增 `location = /__deploy` 反代到
  `http://127.0.0.1:9000/hook` —— 走已有的 80 端口，**腾讯云安全组不用放行 9000**。
- Gitee 填 `http://域名/__deploy`（不是 `/__deploy/hook`，反代已补 /hook）。
- 建议把 `/__deploy` 改成随机串防扫描。

### 教训
- **Node spawn 必须同时监听 `error` 和 `exit`**：只听 exit 的话，ENOENT/EACCES
  这类「进程压根没起来」的错误会变成未捕获异常带崩父进程。凡是
  `Restart=always` 的常驻服务，这个 bug 会伪装成「服务配好了但没反应」。
- **判断「CD 为什么不生效」的顺序**：服务起没起 → Gitee 那边有没有真的发出去
  （WebHook 的「最近请求」）→ 密钥 → 分支。第二条第 0 记录都没有 = 根本没配。
- **端口不通要先分清 timeout vs refused**：timeout = 防火墙/安全组 DROP；
  refused = 进程没监听。本机有代理时更要小心，curl -v 会显示走的是代理。
- **已有 Nginx 就别开新端口**：反代一个 location 比放行安全组端口省事也更安全。

## 2026-09-10 续5 · 云端 5180「active 但打不开」真凶：META_KEYS 未导出

### 现象（最有迷惑性的一种，务必记住）
doctor.sh 报告：
- ② `is-active = active`、`is-enabled = enabled` ✅
- ③ 日志里 `MySQL 已连接` + `已载入 15 名玩家 / 56 个英雄` 全部正常
- ④ `ss -lntp | grep 5180` **只有表头，没有任何监听**
- ⑤ 堆着 **13 个游离的 `node server.js`** 进程
- 外部：`152.136.167.250:5180` connection refused

### 根因一（致命）：`server/store.js` 的 module.exports 漏了 META_KEYS
- server.js 启动 IIFE 里 `Store.META_KEYS.filter(...)` →
  `TypeError: Cannot read properties of undefined (reading 'filter')`（server.js:3288）
- 异常冒出 IIFE → **后面的 `server.listen()` 一行都没执行**。
- 为什么本地测不出来：**本地是 json 驱动，根本不进 `Store.isMySQL()` 分支**。
  这条路径只有线上 MySQL 才会走 —— 测试全绿是假象。
- 修复：`module.exports` 补 `META_KEYS`。

### 根因二：`process.exit('SIGTERM')`
- `process.on('SIGTERM', flushAndExit)` 会把**信号名字符串**传进来，
  `code || 0` 保不住 → `process.exit('SIGTERM')` → ERR_INVALID_ARG_TYPE。
- 结果：进程退不掉 → systemd `stop-sigterm timed out` → SIGKILL →
  日志刷 `Failed with result 'timeout'`、`Failed to kill control group`，
  并**留下游离进程**（就是 ⑤ 里那 13 个）。
- 修复：`const exitCode = typeof code === 'number' ? code : 0;`

### 加固（同类问题不再造成「端口不通」）
1. 启动初始化整体 `try/catch`，**失败也 startListen()**（降级用本地 db.json）；
   另加 15 秒看门狗（unref）防 await 卡死。
2. `Store.META_KEYS` 加 `Array.isArray` 守卫 + 不可用打警告。
3. `DB.users/tokens` 赋值加空值守卫。
4. `store.js` 新增 `DB_STRICT=0`：MySQL 连不上时降级为本地存档而不是 `process.exit(1)`；
   降级时 `isMySQL()` 返回 false，读/写/日志/退出保存自动走文件分支。
   （默认 `DB_STRICT=1` 保持原行为，避免空数据回写覆盖真实存档）

### doctor.sh 自己也有两个假报告（一并修）
- **⑥ 假红**：`awk '{print $2}'` 解析 `ExecStart=/path/node /path/server.js`
  取到的是**脚本**不是 node → 永远报「node 不可执行」。
  正解：先 `sed 's/^ExecStart=//; s/^-//'` 再取第 1 字段，并识别 wrapper。
- **④ 看不出问题**：无监听时只打了表头。现在明确报红 + 附 curl 自检结果。
- 结论第 5 条原推荐 `nohup` 手启（会再造游离进程）→ 改成 pkill + systemctl restart。
- 新增第 6 条：active 但没监听 = 初始化抛异常，去看日志第一条 TypeError。

### 教训（最高价值）
- **`systemd active` ≠ 端口在监听**。判断服务健康必须用
  `ss -lnt | grep :PORT` 或 `curl --noproxy '*' 127.0.0.1:PORT/api/health`。
- **「进程在、依赖也连上了、日志正常，就是不通」→ 一定是 listen() 之前抛异常了**。
  启动 IIFE 里 `await` 之后的任何一步抛错都会把 listen 带走。
- **只在一个分支（MySQL）走到的代码，本地默认配置永远测不出来**。
  凡是 `if (isXxxMode())` 里的新代码，必须想办法在本地也跑一次 Xxx 模式。
  可用 `node -r ./预加载脚本.js server.js` 注入故障来覆盖（本次就这么验的）。
- **`process.exit(signalName)` 是经典坑**：信号处理器第一个参数是字符串。
  凡是 `process.on('SIGxxx', fn)` 直接把 fn 当 exit code 用都会炸。
- **`module.exports` 漏导出**在本地 require 自检就能发现：
  `node -e "const S=require('./server/store.js'); console.log(S.META_KEYS)"`。
  加导出后顺手跑一遍，成本 3 秒。

- 一有敌人就 ReferenceError，被引擎 catch 吞掉（`__MG_TEST` 才会重抛）→ 整个 tick 冻死，行军/下落/碰撞全停
- 修复：把 baseX/baseY 声明前移到 tick 开头 W/H 之后，删除中段重复声明
- 教训：同函数内多 const 声明，把下游要用的提到前面；或全用 function-scoped 命名

### 转刀手感飘（mg-knife.js）
- 根因：原 `drag` 取「拖动起点→当前手指」的方向向量 + 固定速度 130，按住就朝那个方向滑行，松手才停 —— 手指微调不响应、方向切换要划回起点、像在冰面
- 修复：改成「按住屏幕 → 角色朝手指位置移动，靠近后自动减速」(`mSpd = min(S.spd, dist*6)`)
- 加金色目标环作为手指位置反馈；去掉冗余的 tap 走位
- 提示文案从「WASD/方向键 或 拖动 → 移动」改为「按住屏幕指哪走哪」

### 弹球多球失控（pinball.js）四件套
- 现象：无缘无故多出好几个球；翻牌大奖/任务连续开多球；额外球触发坡道/管道时主球被传送
- 根因 1：startMultiball 不封顶，任务链可无限叠球；新球正好生成在中张翻牌 (176,392) 正下方，喷出就翻牌 → 集齐 3 张 jackpot → startMultiball(2) → 再翻
- 根因 2：额外球（bi>0）触发 SAUCER/RAMP/TUBE 时用的是全局状态（saucerHold/onRail），冻结/传送逻辑操作的是 live[0]（主球），看起来像「凭空多球」/「主球瞬移」
- 根因 3：翻牌只判「重叠」，球压在牌上 1.15s 翻牌倒计时结束后立即再翻
- 修复：
  - MAX_LIVE=4：startMultiball 封顶（自动 + 测试 API 都生效）
  - MB_CD=8：自动触发冷却（测试 API force 绕过）
  - grace=1.2s：新球 1.2s 内不翻牌不入洞，喷出时即使穿过翻牌区也不触发
  - saucer/ramp/tube/warp 捕获都加 `ball===live[0]` 限制
  - 翻牌加 cardOver 帧末回写，球必须离开牌面才再次「新压上」
  - onRail 不再 return，多球时其余球照常物理 + 救球 + 漏球
  - kickback/drain 循环跳过 onRailNow + mainFrozen 的 bi=0
