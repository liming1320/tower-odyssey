## ⭐ 云端 ROM 丢失事故根因（当天最重要的发现）
**「只要上传代码，云端 rom 列表就清空」= roms 不在 MySQL META_KEYS，元数据从未持久化**
- `server/store.js` 的 `META_KEYS` 定义哪些全局数据进 game_meta 表，`'roms'` 不在其中

## 17. 模拟器 iframe 高度 CSS bug → 找不到键位设置的根因

**用户反馈**：「控制设置只有重置，清除，关闭，没有设置键位的地方啊」（带截图）

## 18. 模拟器 401 未登录误提示"管理员没上传"（手机看不到游戏）

### 症状
玩家用手机外网 IP 访问 152.136.167.250:5180 看到"管理员还没有上传游戏，敬请期待"，电脑访问 localhost:5180 正常看到 60 个 ROM。

### 根因
不是云端 ROM 库为空，也不是云端代码旧版。
- emulator.js `romList()` 把 `/api/roms` 401（未登录）返回的 `{error:"未登录"}` 用 `(d && d.roms) || []` 吞掉 → 当空数组 → 渲染"管理员还没有上传游戏"
- 手机 localStorage 里 game-token 失效（清理缓存/换浏览器/管家软件清 cookie）
- 但 token 失效前端是 silent 吞掉，玩家完全不知道要重新登录

### 修复
- emulator.js `romList()` 检测 `r.status === 401` → 返回 `{_authError: true}` 标记
- `renderList(roms, authError)` 在 authError 分支显示：
  - 醒目提示："⚠ 登录状态已失效（浏览器缓存被清理 / token 过期）"
  - 说明："电脑正常而手机看不到游戏，多半就是这个原因"
  - 一键【⏏ 退出账号 · 重新登录】按钮（清 token + 刷新跳登录页）
- emulator.js 版本 20260910e → 20260910f
- smoke-emulator.js 加 ⑤.c 测试段：清 token 触发 401 → 验证新提示和按钮

### 验证
冒烟 30/30 全过（之前 26/26，新增 4 条 401 断言）

### 教训
**API 鉴权失败必须明确区分"没数据" vs "没登录"**。
前端 catch 或 fallback 到空数组会把鉴权失败吞掉，让玩家以为是数据问题，定位极其困难。建议：
- 所有鉴权 API 在 fetch 失败/4xx 时记录明确错误码
- 401/未鉴权走专门的 UI 分支（重新登录/提示），不能走"暂无数据"分支
- 顶层 fetch 封装或拦截器统一处理 401，避免每个调用点都要写

- 「按住空格球到顶也弹不出去，在那一直蹦，每次同样高度」：是真 bug。

### 发射死循环根因
- 旧版 `v = 420 + 560*plunger`，max 980。
- 球在发射巷 y=566→GH-16，下落反弹循环。发射后上抛 y 最高 ≈ 980²/(2*1512) ≈ 317px（未考虑重力 1.12x 系数），实际只能到 y≈249（远没到右弧顶 64）。结果：球沿着发射巷底反弹，vy 一直等于 100（bounce 最小值）→ 弹跳幅度恒定 → 用户观察到的「同样的高度」。

### 修复方案
- 发射速度：`v = 1320 + 780*plunger`，min 1380 远超 1.12x 重力下到达 64y 所需的 1211。
- 几何重做：右上角的三角楔 `{(348,120)-(392,60)}` 改为半径 152 的圆顶轨道（右弧/左弧各 14 段折线模拟），球上升后沿顶滑下左弧入局 —— 真正像 Space Cadet 的"右发射 → 顶轨 → 左侧下落"。
- 兜底：困巷 2.2s 自动再击（`laneTimer`），保证再也不死循环。
- 子步 `SUB=4→6`，球速封顶 `1700px/s`，防 SUB 间隧穿。

## 2026-09-10 续2 · WebHook 为什么不生效（用户质疑「不是有 webHook 吗」）

### 排查过程（结论：脚本写了但云端从没装过，且脚本本身有个致命 bug）
1. 实测云端 `152.136.167.250`：
   - 5180 → 200（通）
   - 9000 → **超时 DROP**（进程没起 / 安全组没放行）
   - 8888 → 404（**宝塔面板在跑**）
   - 80 → 200（Nginx 在跑）
   注意：本机 curl 走的是代理 `http://127.0.0.1:56724`，判断端口通不通要区分
   timeout（DROP/防火墙）与 connection refused（进程没监听）。
2. 定位到两个真问题：

**① 致命：`tools/webhook-deploy.js` 的 `runDeploy` 只监听子进程 `exit`，没监听 `error`**
- `spawn('bash', [deploy.sh])` 在 bash 不在 PATH / 脚本路径不对时抛 ENOENT，
  这是 **error 事件而非 exit**，未捕获异常 → **整个 webhook 进程被带崩**。
- systemd `Restart=always` 会不停拉起 → 崩溃循环。
- 外部表现：完全没反应，日志里只有一行 `Unhandled 'error' event`。
- 这正是「配好了但完全不生效」的典型症状，也是我之前误判成「需要手动 restart」的原因。
- **修复**：spawn 前 `fs.existsSync` 检查脚本；加 `child.on('error')` 把原因写进
  `state.last.error`（状态页可读）；`exit` 里加 `if (item.status==='failed' && item.error) return`
  防止覆盖。实测：脚本缺失时返回 `{"error":"deploy.sh 不存在: ..."}` 且进程存活（HTTP 200）。

**② 体验：手改 service 文件太容易出错**
- `deploy/webhook-deploy.service` 里 `ExecStart=/usr/bin/node` 是硬编码，
  宝塔装的 node 在 `/www/server/nodejs/<版本>/bin/node`，照抄必然起不来。
- 新增 `deploy/linux/install-webhook.sh` 一键安装：探测 node（复用 detect-node.sh）、
  openssl 生成密钥、写 systemd（带探测到的 node 绝对路径 + PATH）、
  daemon-reload + enable + restart、本机自检 curl、按监听地址分别打印 Gitee 配置指引。

**③ 免开端口方案（推荐）**
- 新增 `WEBHOOK_HOST`（脚本默认 127.0.0.1）。
- `deploy/nginx/tower-odyssey.conf` 新增 `location = /__deploy` 反代到
  `http://127.0.0.1:9000/hook` —— 走已有的 80 端口，**腾讯云安全组不用放行 9000**。
- Gitee 填 `http://域名/__deploy`（不是 `/__deploy/hook`，反代已补 /hook）。
- 建议把 `/__deploy` 改成随机串防扫描。

### 教训
- **Node spawn 必须同时监听 `error` 和 `exit`**：只听 exit 的话，ENOENT/EACCES
  这类「进程压根没起来」的错误会变成未捕获异常带崩父进程。凡是
  `Restart=always` 的常驻服务，这个 bug 会伪装成「服务配好了但没反应」。
- **判断「CD 为什么不生效」的顺序**：服务起没起 → Gitee 那边有没有真的发出去
  （WebHook 的「最近请求」）→ 密钥 → 分支。第二条第 0 记录都没有 = 根本没配。
- **端口不通要先分清 timeout vs refused**：timeout = 防火墙/安全组 DROP；
  refused = 进程没监听。本机有代理时更要小心，curl -v 会显示走的是代理。
- **已有 Nginx 就别开新端口**：反代一个 location 比放行安全组端口省事也更安全。
